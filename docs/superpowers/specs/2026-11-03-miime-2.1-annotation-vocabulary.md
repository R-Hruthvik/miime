## 1. Problem

Today the AI can only send 8 primitives (`PEN, LINE, RECT, ELLIPSE, ARROW, TEXT,
BLUR, CROP`) with 5 properties (`points`, `color`, `stroke_width`, `text`,
`font_size`). Everything expressive has to be faked by the *caller*:

- `highlight_box` / `spacing_ruler` / `alignment_redline` are not real types —
  they are string aliases mapped onto `RECT` / `LINE` in `str_to_type()`
  (`src/schema.c:188-201`). The stored type becomes `rect`/`line`, so the intent
  is lost on round-trip.
- `stroke_width` is a raw double. There is no notion of "bold" or "marker".
- No fills, no tapered ink, no arrowhead config, no corner radius.
- `som_id` is **parsed and stored nowhere** — `jget(o, "som_id")` is never called,
  so the AI cannot say "circle the element the tool already found for me".
- `layout_mode: "margin_rail"` is accepted by `handle_render` but **ignored** —
  `miime_layout_run()` is never called (`src/layout.c` is dead code from the
  render path). All labels are drawn in-canvas at raw coordinates.

So the AI is forced to do pixel arithmetic and guess placement, which is exactly
what produced the wrong-coordinate renders in earlier sessions.

## 2. Goals / non-goals

**Goals**
1. A richer, *named* primitive vocabulary so the AI describes **intent**, not pixels.
2. Ink control: size presets, tapered strokes, fill modes.
3. Marks that can target an element the tool already knows about (`som_id`).
4. Labels that place themselves (`layout.c` wired into the render path).
5. All of it deterministic and reproducible — same input ⇒ byte-identical output.

**Non-goals**
- Real pointer/mouse driving (see §7 — recommended against, documented anyway).
- Interactive editing, undo UI, or a new GUI.
- Changing the wire protocol (still JSON-RPC over stdio, one line per message).

## 3. Current architecture (grounded in code)

| Concern | File | What exists |
|---|---|---|
| Primitives | `src/annotate.h:8-17` | 8 enum values |
| Annotation struct | `src/annotate.h:39-52` | points[] (4096 doubles), color rgba, stroke_width, text, font_size, blur patch |
| Deserialize | `src/schema.c:200-286` | hand-rolled JSON; reads type/id/source/points/color/stroke_width/text/font_size |
| Serialize | `src/schema.c:295-325` | emits the same 8 fields |
| Render | `src/render.c:34-213` | switch per type; uses `point_count >= 4` gates |
| Sketch engine | `src/sketch.c` + `sketch.h` | **already has** `miime_sketch_hachure()` (diagonal fill) and `miime_sketch_var_stroke()` (variable-width polygon) — both currently unused by render.c except var_stroke for PEN |
| Layout engine | `src/layout.c` + `layout.h` | full margin-rail partitioning, greedy in-canvas placement, force relaxation, port selection, leader routing (S-curve + elbow), obstacle detour via Liang–Barsky. **Never called.** |
| Grounding | `src/grounding.c:358-367` | registry JSON: `[{"id":N,"tag":"...","bounds":[x,y,w,h],"category":C,"contrast":F,"telemetry":"..."}]` with integer SoM ids |
| MCP tools | `src/mcp.c:345-352` | 5 tools, empty `inputSchema` objects |

**Key insight:** the hard rendering work is largely *already implemented*.
`hachure` gives fills. `var_stroke` gives variable ink. `layout.c` gives label
placement + leader lines. Most of this project is **wiring**, not new graphics.

## 4. Proposed schema additions

All new fields are optional; omitted fields keep today's behaviour, so existing
callers (and our task files) keep working.

### 4.1 Per-annotation properties

```jsonc
{
  "id": "err-block",
  "type": "highlight_box",        // now a REAL type, not an alias
  "source": "agent",
  "som_id": 40,                   // NEW: target an element from the registry
  "points": [[20,715],[1895,715],[1895,862],[20,862]],  // still accepts flat [..]
  "color": [1,0.72,0,1],
  "ink": "bold",                  // NEW: thin|regular|bold|marker  (maps to width)
  "stroke_width": [4, 2],         // NEW: [start,end] => tapered; scalar still works
  "dash": "solid",                // NEW: solid|dashed|dotted
  "fill": "hachure",              // NEW: none|hachure|solid
  "fill_color": [1,0.72,0,0.25],  // NEW: defaults to color @ low alpha
  "radius": 12,                   // NEW: rounded corners for rect/callout
  "arrow": "end",                 // NEW: none|end|both|start
  "z": "under",                   // NEW: under|normal|over  (marker/highlight draws under)
  "label": {                      // NEW: first-class label (instead of a separate text annot)
    "text": "Error output jammed",
    "anchor": "auto",             // auto|right|bottom|<port 0..7>
    "leader": "curved"            // curved|elbow|none
  }
}
```

### 4.2 New primitive types

Add to the enum (`annotate.h`) and to `str_to_type`/`type_to_str`:

| Type | Points | Renders as | Backed by |
|---|---|---|---|
| `highlight_box` | 2 or 4 | rect, drawn **under** content, wide translucent stroke | RECT + z=under |
| `spacing_ruler` | 2 | measurement line with end ticks + midpoint label | LINE + tick extension |
| `alignment_redline` | 2 | dashed guide line, full-bleed optional | LINE + dash |
| `callout` | 2 | rounded bubble + tail (Excalidraw's most-used shape) | new: path builder |
| `pin` | 1 (+n) | numbered circular badge at a point | new: ELLIPSE + TEXT |
| `freehand` | N waypoints | smooth pressure-tapered curve through waypoints | **new**: Catmull-Rom → `var_stroke` |
| `circle` | 2 | *perfect* circle (vs `ellipse`'s bounding box) | ELLIPSE with rx==ry |
| `bracket` | 2 | square bracket `[` / `{` for range emphasis | new: polyline |
| `underline` | 2 | thick straight rule under text | LINE with squared caps |
| `strike` | 2 | strikethrough | LINE |

Keeping `rect/line/ellipse/arrow/pen/text` unchanged preserves backward compat.

### 4.3 Ink presets (`ink`)

| name | stroke_width | cap | use |
|---|---|---|---|
| `thin` | 1.5 | round | dense UI, small text |
| `regular` | 2.5 | round | default |
| `bold` | 4 | round | boxes around regions |
| `marker` | 14, alpha 0.35, z=under | square | highlighter |

Explicit `stroke_width` overrides `ink`.

## 5. Semantic targeting (`som_id`)

Today: parsed nowhere. Proposal:

1. At `prepare_ux_canvas`, the registry JSON is already stored in
   `g_state_registry` (`src/mcp.c:236`) as
   `[{"id":N,"tag":"...","bounds":[x,y,w,h],...}]`.
2. Parse it once into a lookup table `som_id -> (x,y,w,h)`.
3. In `miime_schema_deserialize`, if an annotation has `som_id` and its points are
   missing or `[[0,0]]`, expand the points from the box:
   - `highlight_box` / `rect` / `callout` → 4 corners of the box
   - `circle` / `ellipse` → box as diameter
   - `arrow` / `line` → from box edge toward `points[0]` if given, else box center
4. Unknown `som_id` → `send_error` (not silent 0), so the AI learns immediately.

This lets the AI write `{"type":"highlight_box","som_id":40,...}` and get a
correctly-placed box with zero pixel math. It also directly fixes the class of
bug that produced the wrong-coordinate renders earlier.

## 6. Wiring the layout engine (labels)

`handle_render` currently ignores `layout_mode` and never calls
`miime_layout_run()`. Proposed flow:

```
for each annotation with a .label:
    MiimeLayoutItem it = { target box from annotation points,
                           text = label.text,
                           preferred_anchor = parse(label.anchor) }
miime_layout_run(img_w, img_h, items, n, layout_mode, aesthetic,
                 measure_line_via_pango, &pango_ctx, results);
then draw: leader path from results[i].cps, label text at results[i].label_x/y
```

`measure_line_via_pango` is a ~15-line adapter using
`pango_layout_get_pixel_size` (already used in `render.c:136`).

Effect: `layout_mode: "margin_rail"` starts doing what it says — labels go to the
nearest rail, leader lines route around content, obstacle detours kick in.

## 7. Pointer / mouse: three options, assessed

You asked to "try all options". Here is the honest engineering read of each.

### Option A — Coordinates only (status quo, recommended default)
The AI sends points; the renderer draws with the sketch engine. Reproducible,
fast, no timing flakiness. The sketch engine already simulates hand-drawn motion
(jitter, bowing, overshoot) **by design**, deterministically seeded from the
annotation id (`miime_sketch_hash_id`).
**Verdict:** keep as the default. Nothing to build.

### Option B — `freehand` primitive with waypoint interpolation (recommended addition)
The AI supplies sparse waypoints (e.g. 6 points around a shape) and the tool:
1. interpolates a smooth curve (Catmull-Rom),
2. applies pressure taper (width ramps up then tapers at the end),
3. feeds the result to the existing `miime_sketch_var_stroke()`,
4. perturbs along the normal using the seeded PRNG.

This is "pointer-like" in *result* — an organic, hand-drawn-looking stroke — while
remaining fully deterministic and transportable over JSON.
**Verdict:** build it. ~120 lines in a new `freehand.c` + one enum value.

### Option C — Real mouse/pointer control (documented, recommended against)
Having the AI move an actual cursor to draw.

Why it's a downgrade:
- **Non-deterministic:** depends on timing, compositor, window focus, DPI.
- **Not reproducible:** the same prompt yields a different image; you lose the
  ability to diff/re-render or verify.
- **Brittle:** a stray window steals focus mid-stroke.
- **Headless-unfriendly:** the MCP binary links no GTK/display (`Makefile:67`);
  it would need a whole new X11/uinput dependency and a live session.
- **Nothing gained visually:** the sketch engine already produces the human-looking
  wobble *intentionally*; a real drag adds *accidental* wobble, not better art.

If a real pointer is ever genuinely needed (e.g. to operate a *different* app's
canvas), that belongs in a separate browser-automation tool (browser-harness /
TinyFish), not inside this renderer.
**Verdict:** do not build. Documented here so the decision is on record.

### Recommendation
**A + B.** Keep coordinates as the contract; add `freehand` so strokes can look
pointer-drawn. Skip C.

## 8. Implementation plan (PR-sized steps)

1. **Schema v2.1 fields** — add `ink`, `dash`, `fill`, `fill_color`, `radius`,
   `arrow`, `z`, `stroke_width` as width-or-pair. Extend deserialize/serialize.
   No render changes; round-trip tests only.
2. **Real primitive types** — promote `highlight_box`, `spacing_ruler`,
   `alignment_redline` to enum values; add `callout`, `pin`, `bracket`,
   `underline`, `strike`, `circle`. Keep old aliases for one release.
3. **Ink presets + taper** — map `ink` to width/cap; `stroke_width:[a,b]` → taper
   via `var_stroke` for PEN/FREEHAND/LINE.
4. **Fills + radius** — wire `fill` to `miime_sketch_hachure()` / solid; add
   rounded-rect path (radius) for RECT/CALLOUT.
5. **Arrowheads + dash** — extend `miime_sketch_arrow` with head config; add dash.
6. **`freehand`** — Catmull-Rom + taper + PRNG perturbation.
7. **`som_id` targeting** — parse `g_state_registry`, expand points, error on miss.
8. **Layout wiring** — call `miime_layout_run` in `handle_render`; pango measure
   adapter; draw leaders.
9. **Tool schemas** — replace the empty `inputSchema` objects with real JSON
   Schemas so clients can validate and the AI gets field docs.
10. **Golden tests** — per-primitive render hashes; `som_id` expansion tests;
    layout determinism test.

Steps 1–3 are the highest value/lowest risk; 7–8 fix the *correctness* problems
seen in practice; 6 delivers the "pointer-like" look.

## 10. Backward compatibility

- All new fields optional; defaults reproduce today's output exactly.
- Old type aliases (`highlight_box`→rect etc.) keep working; the render of those
  aliases stays identical, so already-produced annotated images do not change.
- `stroke_width` stays valid as a scalar.
- Flat `points` stay valid alongside nested pairs.

## 11. Open questions

1. Should `highlight_box` default to `z: under` (true highlighter) or `normal`
   (current orange outline look we've been producing)? The current task files
   expect an *outline*; changing the default would alter familiar output.
2. `callout`: tail geometry — auto-point at the nearest box edge, or explicit
   `tail:[x,y]`?
3. `pin`: auto-number sequentially from existing pins, or require explicit `n`?
4. Should `spacing_ruler` **auto-compute** tick label text from its own length
   (e.g. "72px") so the AI can't get the number wrong, or stay caller-supplied?
5. Do we want a `dry_run` that returns placements without writing a PNG, for the
   AI's verify loop?
